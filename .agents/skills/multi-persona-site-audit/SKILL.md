# 多ペルソナ・サイト監査スキル (multi-persona-site-audit)

<instructions>

## 1. スキルの目的とポジショニング

本スキルは、Playwright系ツール（`playwright-mcp`）で対象サイトを実際に操作し、複数のペルソナ視点から **証拠接地型（事実ベース）のヒューリスティック監査** を行うためのものです。メインエージェントは個々のブラウザ操作を自ら抱え込まず、**多ペルソナ監査のオーケストレーション層** に徹します。

### これは何か
- 分析の詳細ゴールがまだ固まっていない段階でも使える **「入口／とっかかり」ツール**。ここで得た指摘が、後続の本格的な要件定義・改善計画の起点になる。

### これは何でないか（非目的）
- ❌ 実ユーザーリサーチ（ユーザビリティテスト・アンケート）の代替ではない。
- ❌ 「市場セグメントの気持ちシミュレータ」ではない。潜在層の感情・購買心理などの **定性推測は参考情報にとどめ、実データとして扱わない**。
- LLMペルソナは実在ユーザーの模倣であり、**接地不能な定性推測には免責ラベルを付す**（2・[report-format.md](references/report-format.md) 参照）。

## 2. 中核思想: 証拠接地（事実ベース）

本スキルの品質は「指摘が証拠で裏取りされているか」で決まります。

- **接地できる指摘＝本体（証拠必須）**: 操作フローの詰まり・リンク切れ・視認性/コントラスト・レスポンシブ崩れ・パフォーマンス・アクセシビリティ属性・情報設計の齟齬など、**スクリーンショット / DOM / 操作ログで裏取りできる**もの。
- **接地できない定性推測**: 感情・心理などの推測。出してもよいが、**指摘単位で「これは推論であり実データではない」とラベリング** する。
- **免責の位置づけ**: 免責文は「接地不能な推測」に効かせる安全網であって、**接地作業をサボる免罪符にしない**（＝おためごかしの禁止）。接地可能な指摘を証拠なしで済ませることは許されない。

> [!IMPORTANT]
> 接地の具体的な作法（証拠の取り方・接地/非接地の線引き・免責ラベルの付与基準）は [observation-protocol.md](references/observation-protocol.md) を参照すること。

## 3. アーキテクチャ / 技術前提（確定事項）

| 項目 | 決定 | 理由 |
|---|---|---|
| 実行モデル | **ペルソナを逐次実行**（並列しない。常に1ペルソナのみがブラウザを操作） | Playwright は単一ブラウザセッションを共有するため、並列だと状態を奪い合って破綻する |
| ブラウザ操作の実務 | **`playwright-mcp`（Playwright系ツール）へ委譲** | 本スキルは多ペルソナ監査のオーケストレーション層に徹する |
| ペルソナ間の状態リセット | **各ペルソナ開始時にセッションをリセット**（Cookie/localStorage/ログイン/スクロール位置を持ち越さない）。具体手段（`browser_close` → `browser_navigate` 等）は [observation-protocol.md](references/observation-protocol.md) 2 参照 | 逐次で単一ブラウザを使い回すため、状態漏れを防ぐ |
| サブエージェント採用の目的 | **並列速度ではなく「視点の独立性」** | 各ペルソナを独立コンテキストで走らせ、他ペルソナの所感を見せないことでトライアンギュレーション（複数独立指摘＝高信頼）の前提を守る |
| ペルソナ数 | **1回あたり 3〜6 体** | 過負荷防止。**サブエージェント起動数（3〜6）はメインのコンテキスト保護（13件ループ規約）の観点で安全圏**。1ペルソナ内のページ操作数は別途下段（ページ数上限行）および [persona-scenarios.md](references/persona-scenarios.md) 5 の上限に従う |
| デバイス/ビューポート | **PC(1025px以上)／モバイル(599pxまで)を基本**、タブレットは必要時（`browser_resize` で検証） | 主要な閲覧文脈を最小コストで押さえる |
| ページ数上限 | **1ペルソナあたり主要導線5〜8ページ程度** | 1ペルソナ内の総操作が多数（13件目安超）に及ぶ場合は、13件ループ規約に従い当該ペルソナの分割／セッション分割（New Chat）を提案 |
| 認証必須サイト | **初版はスコープ外（公開ページのみ）**。将来拡張 | 認証時は `minimal-security-guidelines.md` 準拠でユーザー手動ログイン前提 |

## 4. ペルソナ設計（概要）

ペルソナは以下の4軸で整理し、対象サイトごとに数体を選抜する（毎回全部は起動しない）。

| 軸 | 内容（例） |
|---|---|
| (a) 専門家レンズ | サイトアナリスト／UX・UIデザイナー／フロントエンド品質（パフォーマンス・アクセシビリティ・SEO・セマンティクス）／アクセシビリティ特化（キーボード操作・フォーカス順序・ARIA・コントラスト等に絞った独立レンズ。詳細は [persona-scenarios.md](references/persona-scenarios.md) 1(a)） |
| (b) ユーザーセグメント | ファネル軸: 情報収集フェーズ（潜在層）／比較検討（顕在層）。難易度軸: 単純導線 vs 複雑導線 |
| (c) デバイス文脈 | モバイル／タブレット／PC（`browser_resize` で切り替えて検証） |
| (d) 競合ベンチ | 競合・同業サイトとの比較（独立軸） |

### ペルソナ定義の作法（要点）
- ✅ **タスクシナリオ（何を操作するか）と評価レンズ（どの観点で観るか）を濃く定義** する。
- ✅ 年齢・職業・背景ストーリーなどの **作り込みは薄く** する（作り込むほど"観察"より"役割演技"に寄り、ハルシネーションが増えるため）。
- アクセシビリティ・ペルソナの接地点は **アクセシビリティツリー / ARIA属性 / コントラスト比 / キーボード操作可否 / フォーカス順序** といった機械的に検証できる事実に限定する（「スクリーンリーダー体験の感想」は推測扱い）。

> [!IMPORTANT]
> 4軸の **標準タスクシナリオ雛形**、ペルソナ選抜の考え方、競合ベンチ軸（4-4）の運用詳細は [persona-scenarios.md](references/persona-scenarios.md) に集約している。Phase0で判定したサイト種別に応じて、メインエージェントが雛形を微調整して各ペルソナへ渡す（**ハイブリッド方式**）。

## 5. 安全制約（絶対遵守）

- **CV関連ページでの状態変更操作は厳禁とする**。具体的な操作可否の線引きや定義などの詳細は [observation-protocol.md](references/observation-protocol.md) を参照すること。
- プロジェクト規約の事前承認・破壊的操作防止ポリシー（[`hitl-policy.md`](../../rules/hitl-policy.md)）を遵守する。
- 認証必須ページは初版スコープ外。必要時は [`minimal-security-guidelines.md`](../../rules/minimal-security-guidelines.md) 準拠でユーザー手動ログインを前提とする。

## 6. ワークフロー（Phase 0〜3）

> [!CAUTION]
> **サブエージェント（ペルソナ）の複数起動は y/n 事前承認が必須**（[`subagent-policy.md`](../../rules/subagent-policy.md)）。Phase1 へ進む前に、必ず起動計画を提示してユーザー承認を得ること。無言での自律起動は禁止（`PreToolUse` フックにより物理ブロックされる）。

### Phase 0: 対象確認（軽量に保つ）
- 対象サイト（URL）を確認する。
- メインエージェントが **サイト種別を自動推定**（EC／コーポレート／メディア／SaaS LP 等）→ ユーザーへ一言確認する。
- 分析目的は **任意・デフォルトあり**（未指定なら「全体的な改善のとっかかり探索」）。
- 起動するペルソナ（3〜6体）を **自動マッピング案として提示 → ユーザーが一言で承認/差し替え**（[persona-scenarios.md](references/persona-scenarios.md) の軸から選抜）。
- 競合ベンチ軸を含む場合: 競合URL未指定なら **AIが演じる同業他社の役設定をユーザーへ確認**（4-4 / [persona-scenarios.md](references/persona-scenarios.md)）。
- ※本スキルは"入口"用途のため、詳細ゴール・成功基準の事前定義は求めない。

---

**【承認ゲート】** ペルソナ選抜案とページ範囲を提示し、Phase1（サブエージェント逐次起動）へ移行してよいか y/n で確認する。
- ※Phase0 の承認ゲートでページ範囲を確定し、**1ペルソナで13操作超が見込まれる場合は起動前に範囲縮小またはセッション分割を合意しておく**（サブエージェント実行中の中断・多段確認を避ける）。

### Phase 1: 各ペルソナによるサイト操作（逐次）
- 各ペルソナを **1体ずつ逐次起動**する（専用のサブエージェント型は無いため汎用的な組み込みサブエージェントを用いる。[`workflow.md`](../../rules/workflow.md) 第2アプローチ準拠）。**常に1ペルソナのみがブラウザを操作** し、開始時にセッションをリセットする（`browser_close` 後の `browser_navigate <開始URL>` 等でセッションをリセット。具体手順は [observation-protocol.md](references/observation-protocol.md) 2）。
- **タスクシナリオ＋観測プロトコル**（[observation-protocol.md](references/observation-protocol.md)）に従って操作し、**証拠（スクリーンショット / DOM / 操作手順 / 詰まった箇所）を持ち帰る**（"感想"でなく"証拠"）。
- 各サブエージェントへ渡す指令書は [subagent-brief-template.md](references/subagent-brief-template.md) の雛形を用いる（ルール継承漏れ・文脈汚染の防止）。
- 各サブエージェントは Artifact ログ（`tasks/[サイト名]-audit-report/[CurrentSessionName]_[SubagentName]_ARTIFACTS.md`）に成果物・変更パス・スクリーンショット保存先を追記する。
- ブラウザ操作は `playwright-mcp`（Playwright系ツール）を用い、**自己流スクリプト（車輪の再発明）を禁止**する。

### Phase 2: 統合（メインエージェント）
- 単なる寄せ集めでなく、**重複排除・重大度で重み付け・トライアンギュレーション**（複数ペルソナが独立に同一指摘＝高信頼）を実施する。
- 統合手順の詳細は [report-format.md](references/report-format.md) を参照し、レポートのドラフトをマークダウンファイルとして一時的に作成する。

### Phase 3: 第三者監査（qa-auditor）
- サブエージェントでの各ペルソナの回答およびメインエージェントによる統合・ドラフト作成後、**必ず独立第三者の `qa-auditor` を用いて第三者チェックを実施**する。
- 起動時は [`workflow.md`](../../rules/workflow.md) 第1アプローチ（オーバーソウル）に則り、`utils/generate_subagent_prompt.py` を用いて文脈（レポートドラフト、タスク概要など）を注入して起動すること。
- `qa-auditor` から「PASS」の判定を受けるまではユーザーへの完了報告（レポートの納品）を行わない。

### Phase 4: 提供（成果物）
- **固定フォーマット**（5要素・厳密固定。詳細は [report-format.md](references/report-format.md)）で提供する。各改善仮説は以下の5要素を必ず備える:
  - 改善仮説（優先度: 高/中/低）
  - 根拠（証拠: スクリーンショット / DOM抜粋 / ログ抜粋）
  - インパクト / 工数の目安
  - 推論注記（接地不能な要素を含む場合のみ「【推論】…（実データではない）」。無ければ「なし」）
  - 裏取り（トライアンギュレーション有無＝複数ペルソナの独立一致）
- レポート末尾には **固定免責文**（[report-format.md](references/report-format.md) 3）を全体の安全網として必ず挿入する。
- **最終的なレポートファイルおよび取得したすべての証拠（スクリーンショット等の参照キャプチャ画像）は、`tasks/[サイト名]-audit-report` ディレクトリにまとめて格納**して納品する（一時ディレクトリでなく永続的な成果物ディレクトリとして扱う）。

## 7. プロジェクト規約の遵守事項

- **サブエージェント複数起動は y/n 事前承認が必要**（[`subagent-policy.md`](../../rules/subagent-policy.md)）。HITL（[`hitl-policy.md`](../../rules/hitl-policy.md)）を最上位命令として遵守する。
- 成果物（スクリーンショット・レポート）は **`tasks/[サイト名]-audit-report/` 配下に格納し、レポート内の画像リンク切れを防ぐ**こと。ルートや他ディレクトリへの配置は禁止。
- なお、[`workflow.md`](../../rules/workflow.md) では作業ファイルを `tasks/[project]/tmp/` 配下に限定する規約があるが、本スキルの成果物は監査レポートとして永続的に残す性質上、`tasks/[サイト名]-audit-report/`（永続ディレクトリ）へ格納することを **意図的な例外** として扱う。
- 各サブエージェントに **Artifact ログ（`tasks/[サイト名]-audit-report/[CurrentSessionName]_[SubagentName]_ARTIFACTS.md`）を義務付け**（[subagent-brief-template.md](references/subagent-brief-template.md) に明記）。
- タスク完了後は **不要になった一時ファイル（`[CurrentSessionName]_[SubagentName]_ARTIFACTS.md`など）・サブエージェントをクリーンアップ**（削除前にユーザーへ対象提示 → y）。**成果物ディレクトリ（`tasks/[サイト名]-audit-report/`）自体やレポート・キャプチャ画像は削除せず残す**こと。破壊的操作は [`hitl-policy.md`](../../rules/hitl-policy.md) の認知的チェックポイントを遵守する。
- 提供ツール（`playwright-mcp`）を活用し、**車輪の再発明（自己流スクリプト）を禁止**する。
