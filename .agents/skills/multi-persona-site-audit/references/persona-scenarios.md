# ペルソナ設計と標準タスクシナリオ雛形

本ファイルは、[SKILL.md](../SKILL.md) 4 の詳細版です。4軸のペルソナ整理、標準タスクシナリオ雛形（ハイブリッド方式の元ネタ）、選抜の考え方、競合ベンチ軸の運用をまとめます。

> [!IMPORTANT]
> - **雛形はそのまま使うものではない**。Phase0 で判定したサイト種別（EC／コーポレート／メディア／SaaS LP 等）に応じて、メインエージェントが微調整して各ペルソナへ渡す（**ハイブリッド方式**）。
> - ペルソナ定義は **「タスクシナリオ（何を操作するか）＋評価レンズ（どの観点で観るか）」を濃く**、**背景ストーリー（年齢・職業・人生観）は薄く**する。作り込むほど"観察"より"役割演技"に寄り、ハルシネーションが増える。

---

## 1. 4軸のペルソナ・カタログ

### (a) 専門家レンズ
| ペルソナ | 評価レンズ | 主な接地点（証拠） |
|---|---|---|
| サイトアナリスト | 情報設計・導線・CVへの動線・回遊性・離脱誘発点 | 遷移ログ・スクロール深度・クリック対象の発見容易性・パンくず/ナビ構造(DOM) |
| UX・UIデザイナー | 視認性・レイアウト・タイポグラフィ・一貫性・レスポンシブ挙動 | スクリーンショット（PC/モバイル）・崩れ箇所・余白/整列・フォントサイズ・タップ領域サイズ |
| フロントエンド品質 | パフォーマンス・アクセシビリティ・SEO・セマンティクス | ネットワークログ・コンソールエラー・アクセシビリティツリー/ARIA・見出し階層・メタ情報(DOM) |
| アクセシビリティ特化 | キーボード操作・フォーカス順序・ARIA/role・コントラスト・見出し階層・alt/ラベル | アクセシビリティツリー・ARIA/role属性・コントラスト比実測・フォーカス移動のスクリーンショット（機械的事実に限定） |

### (b) ユーザーセグメント
| 軸 | ペルソナ例 | タスクの性質 |
|---|---|---|
| ファネル: 情報収集フェーズ（潜在層） | 「まだ課題が漠然としており、まず何のサイトか把握したい人」 | トップから概要把握、"このサイトは自分向きか"を数十秒で判断できるか |
| ファネル: 比較検討（顕在層） | 「具体的なニーズがあり、条件・料金・実績を確かめたい人」 | 料金/仕様/事例ページへ最短で到達できるか、比較材料が揃うか |
| 難易度: 単純導線 | 「1〜2クリックで目的達成を期待する人」 | 主要CTAへの到達しやすさ |
| 難易度: 複雑導線 | 「絞り込み・検索・多段フォーム等を要する目的を持つ人」 | 複雑操作の詰まり・迷子・戻れなさ |

### (c) デバイス文脈
- **PC(1025px〜)／タブレット(600px〜1024px)／モバイル(0px〜599px)を基本**とし、`browser_resize`（Playwright-MCP ツール）でビューポートを検証。
- デバイス軸は単独ペルソナにするより、(a)(b) のペルソナに **「このビューポートで観よ」という指定を重ねる** 使い方が基本。
- **独立ペルソナ化の判断基準**: 独立したデバイスペルソナ化は、**モバイル特有の破綻（タップ領域の狭さ・意図しない横スクロール・固定ヘッダーによる被り等）を主目的に検証する場合に限る**。それ以外は (a)(b) ペルソナに「このビューポートで観よ」と重ねる運用を基本とする。


### (d) 競合ベンチ
- 競合・同業サイトとの比較を行う独立軸。運用は本ファイル 4 を参照。

> [!CAUTION]
> **複雑導線・ECペルソナの操作範囲（安全制約の具体化）**: 検索・絞り込み・並び替え等の **冪等操作（サーバ状態を変えないGET）は操作可**。一方、**カート追加・決済・会員登録・問い合わせ送信などの状態変更操作は観測外**（[observation-protocol.md](observation-protocol.md) 5）。とくにECでは **カート/購入フローのUXが丸ごと観測外＝許容損失** となるため、その旨を必ず成果物へ明記する（黙って省略しない）。

## 2. 標準タスクシナリオ雛形

各ペルソナへ渡すシナリオは「開始URL → 実行タスク → 観測レンズ → 証拠取得ポイント」で構成する。以下は雛形。`< >` はサイト種別に応じてメインエージェントが埋める。

### 雛形A: サイトアナリスト（導線・情報設計）
```
開始URL: <トップページURL>
実行タスク:
  1. トップページで「このサイトの目的・提供価値」を5秒/15秒/30秒の段階で把握できるか観察
  2. 主要CTA（<問い合わせ/購入/資料請求など>）への最短到達を試みる（クリック数を記録）
  3. グローバルナビ・パンくず・フッターから主要導線（<料金/事例/会社概要など>）へ回遊
観測レンズ: 情報の発見容易性 / 導線の明快さ / 離脱を誘発する分岐や行き止まり
証拠取得: 各遷移のスクリーンショット・クリック対象のsnapshot(ref)・到達クリック数・詰まった箇所
安全制約: CV関連ページは閲覧のみ（入力・送信しない）
```

### 雛形B: UX・UIデザイナー（視認性・レスポンシブ）
```
開始URL: <トップページURL>
実行タスク:
  1. PC(1440x900等)で主要ページ<3〜5ページ>のファーストビュー〜フッターをスクリーンショット（browser_resize → browser_snapshot で確認 → browser_take_screenshot）
  2. モバイル(390x844等)に browser_resize で切り替え、browser_snapshot でDOM/レイアウト更新検知後に同ページをスクリーンショット。横スクロール発生・要素被り・タップ領域の狭さを確認
  3. 主要CTAボタン・本文・見出しのコントラスト/フォントサイズの妥当性を確認（browser_evaluate等）
観測レンズ: レイアウトの崩れ / 一貫性 / 可読性 / レスポンシブ挙動
証拠取得: PC/モバイル両方のスクリーンショット（崩れは該当要素のsnapshotも）・コントラスト比の実測値
安全制約: CV関連ページは閲覧のみ
```

### 雛形C: フロントエンド品質（パフォーマンス/アクセシビリティ/SEO）
```
開始URL: <トップページURL>
実行タスク:
  1. 主要ページを開き、コンソールエラー・ネットワークの重いリソース（大画像/未圧縮）を確認
  2. アクセシビリティツリー/ARIA属性・見出し階層(h1..h6)・alt属性・フォーカス順序・キーボード操作可否を確認
  3. <title>/meta description/OGP/構造化データの有無を確認
観測レンズ: 表示速度の足かせ / アクセシビリティ属性の欠落 / SEO基本要件 / セマンティクス
証拠取得: コンソールログ・ネットワークログ・アクセシビリティ属性のDOM抜粋・メタ情報のDOM抜粋
安全制約: CV関連ページは閲覧のみ
接地上の注意: 「速い/遅いと感じる」等の主観は避け、リソースサイズ・件数・エラー有無という機械的事実で述べる
守備範囲: アクセシビリティ観点は概況把握に留め、キーボード操作・フォーカス順序の精査は雛形E（アクセシビリティ特化）に委ねる（重複回避）
```

### 雛形D: ユーザーセグメント（潜在層/顕在層 × 単純/複雑導線）
```
開始URL: <トップページURL または 想定流入URL>
ペルソナ設定（薄く）: <例: 比較検討中の顕在層。料金と導入実績を確かめたい>
実行タスク:
  1. 上記ニーズを満たす情報（<料金/事例/仕様など>）を探し、到達までの操作を記録
  2. 目的情報が「揃っているか/不足しているか」を観察
観測レンズ: 目的達成のしやすさ / 情報の過不足 / 迷い・引き返しの発生点
証拠取得: 遷移スクリーンショット・到達クリック数・詰まった/迷った箇所のスクリーンショット
安全制約: CV関連ページは閲覧のみ（例: 資料請求フォームは開いて構成を見るだけ）
免責: 「不安を感じる」「魅力的に映る」等の感情記述は推論ラベルを付す
```

### 雛形E: アクセシビリティ特化
```
開始URL: <トップページURL>
実行タスク:
  1. キーボードのみ（Tab/Shift+Tab/Enter）で主要導線を辿れるか
  2. フォーカスリングの可視性・フォーカス順序の論理性を確認
  3. 画像alt・フォームラベル・ランドマークロール・見出し階層・コントラスト比を確認
観測レンズ: 機械的に検証できるアクセシビリティ事実のみ
証拠取得: アクセシビリティツリー・ARIA/role属性のDOM抜粋・コントラスト比実測・フォーカス移動のスクリーンショット
接地の線引き: 「スクリーンリーダー利用者はこう感じる」は推論扱い。属性の有無・比率・操作可否は接地事実
守備範囲: パフォーマンス・SEO は範囲外（雛形C の担当）。本ペルソナはキーボード操作・フォーカス・A11y属性に集中する
安全制約: CV関連ページは閲覧のみ
```

## 3. ペルソナ選抜の考え方（Phase0 の自動マッピング案）

- **毎回 4軸すべてを起動しない**。サイト種別と（あれば）分析目的から 3〜6 体を選ぶ。
- サイト種別別の目安（あくまで初期案。ユーザーが一言で差し替え可能）:
  - **EC**: サイトアナリスト(導線) / UX・UI(モバイル) / 顕在層(比較検討) / フロントエンド品質(パフォーマンス) 〔＋競合ベンチ〕
  - **コーポレート**: サイトアナリスト / UX・UI / 潜在層(情報収集) / アクセシビリティ
  - **メディア**: フロントエンド品質(パフォーマンス/SEO) / UX・UI(可読性) / 回遊(サイトアナリスト) / アクセシビリティ
  - **SaaS LP**: 顕在層(比較検討) / サイトアナリスト(CTA導線) / UX・UI / 競合ベンチ
- 提示形式: 「今回はこの N 体を起動する案です（各1行の役割）。差し替え・追加はありますか？」→ **ユーザーが一言で承認/差し替え**。

## 4. 競合ベンチ軸の運用（4-4）

- 競合URLは **ユーザー任意指定**。
- **未指定の場合は、AIが同業他社になりきって（役割演技で）対象サイトを批評する**。この際、**役設定の詳細（想定する競合像・立場・強みの置きどころ）を事前にユーザーへ確認** する。
  - 確認例: 「競合URL未指定のため、AIが『<同カテゴリでシェア上位／価格訴求型／プレミアム訴求型など>』の同業他社を演じて対象サイトを批評します。この役設定でよいですか？」
- **接地上の注意（重要）**:
  - この役割演技ペルソナの **「対象サイトの観測」は接地できる**（実際に見て回った事実）。
  - 一方、**「競合ならどう攻めるか」という競争戦略的解釈は推測** である。
  - したがって当該指摘のうち戦略的解釈部分には **免責ラベルを付す**（[report-format.md](report-format.md) の免責基準に整合）。
  - ※競合ベンチの主産物である「競合ならどう攻めるか」の戦略解釈は本質的に推測であり、**免責ラベル付きの参考情報**として扱う。接地できるのは対象サイトの観測事実のみである点に留意する（推測部分をあたかも実データのように提示しない）。

## 5. ページ数・スコープの上限

- **1ペルソナあたり主要導線 5〜8 ページ程度** に絞る。
- 「13件ループ規約」の適用単位を混同しないこと:
  - **サブエージェント起動数（1回あたり 3〜6 体）** はメインエージェントのコンテキスト保護の観点で管理する（[SKILL.md](../SKILL.md) 3）。
  - **1ペルソナ内のページ操作** が多数（13件目安を超える）に及ぶ見込みの場合は、[`workflow.md`](../../../rules/workflow.md) の「13件以上ループは要セッション分割」規約に従い、当該ペルソナの範囲縮小またはセッション分割（New Chat）をユーザーへ提案してから続行する。
- **起動前合意**: ページ範囲は Phase0 の承認ゲートで確定し、1ペルソナで13操作超が見込まれる場合は起動前に範囲縮小またはセッション分割を合意しておく（サブエージェント実行中の中断・多段確認を避ける）。
