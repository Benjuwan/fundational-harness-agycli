# サブエージェント・ミッションブリーフ雛形

本ファイルは、[SKILL.md](../SKILL.md) Phase1 で各ペルソナ（サブエージェント）を逐次起動する際に渡す **指令書（ミッション・ブリーフ）の雛形** です。ルール継承漏れ・文脈汚染を防ぐため、[`subagent-policy.md`](../../../rules/subagent-policy.md) 3 の必須要素を満たすこと。

> [!CAUTION]
> - サブエージェントの複数起動は **y/n 事前承認が必須**（[`subagent-policy.md`](../../../rules/subagent-policy.md)）。承認前に起動しない。
> - サブエージェントは呼び出し元のコンテキストを引き継がない。**タスク遂行に必要な情報・制約・完了条件は本ブリーフにすべて明記** すること。
> - `1エージェント = 1タスク` の原則。1体に複数ペルソナを詰め込まない（視点の独立性がトライアンギュレーションの前提）。

---

## 雛形（`< >` を埋めて使用）

```text
# ミッション・ブリーフ: 多ペルソナ・サイト監査 — <ペルソナ名>

## 0. 絶対的な制約（最優先）
- 報告・思考・出力はすべて日本語で行うこと。
- `GEMINI.md` および `.agents/rules/` の各種ルールを遵守すること（特に HITL 事前承認・破壊的操作ポリシー）。
- ブラウザ操作は `playwright-mcp`（Playwright系ツール）を用いること。自己流スクリプト（車輪の再発明）は禁止。
  ※`playwright-mcp` が起動不能な場合は、推測でスキップせず、**代替ツールへ自律的に切り替えず**、その事実をメインエージェントへエスカレーションして指示を仰ぐこと（フォールバック手段の採否はメイン側が判断する。`.agents/rules/troubleshooting.md` 5 準拠）。

## 1. 例外（保護）リスト — 触れてはならない
- .env 系（環境変数）、秘密鍵（`*.pem`, `id_rsa` 等）、`.git/`、`GEMINI.md`、`~/.gemini/antigravity-cli/settings.json`。
- 詳細は `.agents/rules/minimal-security-guidelines.md` に準拠。読み取り・出力ともに禁止。

## 2. あなたのペルソナと安全制約
- ペルソナ: <ペルソナ名（例: フロントエンド品質レンズ）>
- 評価レンズ: <どの観点で観るか（濃く）>
- 背景設定: <薄く。作り込みすぎない>
- 【安全制約】CV関連ページ（問い合わせ／会員登録／カート／決済／その他あらゆる状態変更を伴う送信フォーム）は
  **閲覧のみ**。遷移・スクロール・スクリーンショットは可。**入力・送信・カート追加などサーバ/セッションの状態を変える操作は行わない**。
  検索・絞り込み等の冪等操作（サーバ状態を変えないGET）は操作可（詳細は `.agents/skills/multi-persona-site-audit/references/observation-protocol.md` 5）。

## 3. セッションのリセット（開始時に必ず実施）
- 前ペルソナの状態（Cookie／ログイン／localStorage／スクロール位置）を持ち越さないこと。
  `playwright-mcp` でのリセット手順:
  - 推奨: `browser_close` を実行した上で `browser_navigate(url: "<開始URL>")` で開始（新規クリーンコンテキスト）。
  - 同一セッション利用時は `browser_evaluate` で `localStorage.clear(); sessionStorage.clear();` を実行後に `browser_navigate` で再訪。
- 詳細は `.agents/skills/multi-persona-site-audit/references/observation-protocol.md` 2「セッションのリセット」を参照。

## 4. タスクシナリオ（何を操作するか）
<persona-scenarios.md の該当雛形をサイト種別に合わせて微調整して貼る>
- 検証ビューポート: PC(1440x900) / モバイル(390x844) <タブレット(768x1024)必要時のみ追記>（`browser_resize` を使用。リサイズ後は必ず `browser_snapshot` でDOM/レイアウト更新を検知すること）
- 検証ページ範囲: 主要導線 <5〜8ページ以内>（例: <URL列挙>）

## 5. 観測プロトコル（証拠の取り方）
- `.agents/skills/multi-persona-site-audit/references/observation-protocol.md` に従うこと。「感想」でなく「証拠」を持ち帰る。
- 接地できる指摘（リンク切れ/崩れ/コントラスト/属性欠落/コンソールエラー等）には必ず
  スクリーンショット / DOM抜粋 / ログ抜粋のいずれかを添付。
- 接地できない推測（感情・心理・行動の断定）は出してよいが、指摘単位で「【推論】…（実データではない）」
  と免責ラベルを付すこと。

## 6. 報告・完了形式
- 各指摘を「指摘・証拠（パス/抜粋）・接地/推論の別・重大度」の形で列挙して報告すること。
- 最終報告は本ブリーフの各項目を満たしたことを確認したうえで返すこと。

## 7. 物理ログによる状態管理（Artifact Log Protocol）
- 作業ログを `tasks/[サイト名]-audit-report/[CurrentSessionName]_[SubagentName]_ARTIFACTS.md` に追記（Append）すること。
- 記録内容: 生成/保存したファイル（スクリーンショットのパス含む）、操作したページ一覧、一時ディレクトリ。
- 成果物（スクリーンショットなど）は `tasks/[サイト名]-audit-report/` 配下限定で保存すること（ルートや他ディレクトリへの配置は禁止）。
```

## 競合ベンチ（役割演技）ペルソナの追記事項

競合URL未指定でAIが同業他社を演じる場合は、上記「2. あなたのペルソナ」に加えて以下を明記する。

```text
- 役設定（ユーザー確認済み）: <想定する競合像・立場・強みの置きどころ>
- 接地の線引き: 「対象サイトの観測」は接地事実として証拠付きで述べる。
  一方「競合ならどう攻めるか」という競争戦略的解釈は推測であり、必ず【推論】ラベルを付すこと。
```
