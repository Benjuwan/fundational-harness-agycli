# プレゼンテーションスライダー制作スキル (Presentation Slider Creator)
このスキルは、ユーザーから与えられた原稿（テキスト、URL、マークダウンなど）をもとに、プレゼンテーション用スライド（Marp）を作成するための厳格なワークフローを定義します。  
※「`Marp for VSCode`（エディタ上でリアルタイムにスライドのプレビューを見ながら執筆できる拡張機能）」については、ユーザーから拡張機能に関する言及が確認できた場合に提示してください。

<instructions>

## 絶対的ルール
AIが一度に大量のスライドを生成すると、1ページあたりの情報過多やデザインの破綻を引き起こします。AIは自律的な一括生成を放棄し、**必ず以下の実行ワークフローフェーズに従ってステップ・バイ・ステップで作業を進め、各フェーズでユーザーの承認（Approve）を得ること**。スライドは Markdownベースで記述しやすい **Marp** 形式とします。

## 実行ワークフロー
ユーザーに、Marpの説明（シンプルで簡易なスライド作成ツールであることやマーメイド図や図解の作成・描画には対応していないことなど）と、マークダウン形式での記述が必須なこと。マークダウンの簡易説明を初めに行うこと。

> [!NOTE]
> **既存のプレゼン用ファイルがある場合**：
> ユーザーから「このプレゼンファイルを開いて」などプレゼン資料の表示や確認を求める入力があった場合は、通常のフェーズ1〜3をスキップし、フェーズ4の「2. プレビューの案内（または実行）」に記載されている「AIによるブラウザアクセス代行処理」を即座に実施し、ユーザーに表示したうえで編集や修正の有無を確認してください。

### フェーズ1：要件定義とアウトライン
情報をスライド形式に落とし込むための「構成案」を作成し、合意をとります。この際、ユーザーに参照ドキュメント資料やファイルがあるかを確認してください。  
また、一切情報がない状態（ゼロベース）からのスタートの場合は[壁打ちスキル](../grill-me/SKILL.md)を通じて詳細を詰めていくフローをユーザーに提案すること。

1. **インプットの解析**: ユーザーから渡されたテキスト、URL、またはテーマの指示を読み込みます。
   - **【参照URLの読み込みに関する原則】**: ユーザーからURLが提供された場合、表示が切り替わるWebページ（動的ページ）にも正確に対応できるよう、必ず最初に Playwright MCP を使用してページ情報（コンテンツ）を取得・解析すること。
   - **【情報抽出の原則（※スライドの新規制作の場合のみ適用）】**: ユーザーから参照情報（ドキュメントやテキストファイル、参照URLなど）を受け取った場合は明示的な指示がない限り、AI自身の事前知識や独自の考察（一般論など）を勝手に補完・混入させず、**必ずその参照情報の内容に忠実な要約スライドの作成に努める**こと。この場合、次の工程（ヒアリング事項の確認）で「*参照情報（`<ユーザーからの参照ファイルパスやURLなどを出力する>`）が確認できたので『要約スライドの作成依頼』と認識します*」と、**一言一句違わずユーザーへ必ず報告する**こと。
2. **ヒアリング事項の確認**: 以下の点が不明な場合はユーザーに確認してください。※必要に応じて[壁打ちスキル](../grill-me/SKILL.md)を活用すること
   - 全体の想定スライド枚数（おおよそのボリューム）
   - トーン＆マナー（堅め、カジュアル、視覚的アピール重視など）
   - 画像などの素材（アセット）要件：使用したい画像ファイル（ロゴ、図解、スクリーンショットなど）の有無と保存先パス。または、AIによるイメージ画像の生成（`generate_image` ツールなどの利用）を希望するか。
3. **アウトラインの提示**: インプット情報をもとに、「各スライドのタイトルと概要（箇条書き）」をまとめたアウトライン（構成案）を作成し、ユーザーに提示します。※この際、ユーザーから「文字カラーリングや文字サイズ」に関する明示的な指定がなければ、原則として文字色は **color: #333;** 、本文の文字サイズは **font-size: 20px;** とします。
4. **【認知的チェックポイント】**
   - ユーザーからアウトラインに対する「OK」や「修正指示による合意」を得るまで、記述の生成には進まないこと。

### フェーズ2：AIによる画像生成・アセット準備（※ユーザー希望時のみ）
ユーザーがスライド用の画像生成をAIに希望した場合、または素材の事前配置を必要とする場合に実行するフェーズです。
- ※このフェーズは「画像の生成・準備」のみに特化します。スライドのテキスト生成作業は行いません。
- ※全スライドへの画像生成など「大量の画像生成」が依頼された場合は、処理時間や制限（トークン消費など）のデメリットをユーザーに伝え、「まずは5枚分まで画像を生成しましょうか？」など段階的に進める判断を仰いでください。

1. **画像要件のすり合わせ**: どのようなイメージ画像（イラスト、写真風、アイコンなど）が必要かをヒアリングします。
   - ※フェーズ1で決定した「トーン＆マナー（テイスト）」を確実に引き継ぎ、生成するすべての画像で画風に一貫性（統一感）を持たせるようにしてください。
   - ※AI画像生成フェーズに入った初回時に必ず、AIが生成した画像やユーザーが指定した画像の「著作権・ライセンス・商用利用の取り扱い」に関する注意事項を明確に伝達し、自己責任での利用となる旨を合意してください。
2. **画像の生成と保存**: AI自身が画像生成ツールを使用して画像を生成し、作業用ディレクトリ（例: `tasks/[プロジェクト名]/tmp/`）に保存します。ツールが失敗（エラー）した場合は、ユーザーに伝えて「再試行するか」「スキップ（画像なしで進める）するか」の判断を仰いでください。
3. **【認知的チェックポイント】**
   - 生成した画像（またはユーザーが配置した画像）を確認し、スライドに使用する素材として合意を得ること。

### フェーズ3：テンプレート検証（お試し生成）とスタイル合意
全スライドを一気に生成する前に、基本となるデザインスタイルと「1枚目のスライド」のみを生成して検証します。

1. **基本設定（デザイン設定）の定義**: 
ヘッダーのスタイル指定（`marp: true`, `theme`, 色指定など）を記述します。
2. **1スライドのみの実装**: フェーズ1で合意したアウトラインの「最初のコンテンツスライド（または表紙と2枚目）」のみをテキストとして生成し、提示します。
   - **画像の組み込み**: フェーズ1で指定された画像パスや、フェーズ2でAIが生成した画像がある場合、Marp記法（例: 背景画像なら `![bg right:40% contain](画像パス)`、通常挿入なら `![width:400px](画像パス)`）を用いてスライドに組み込みます。縦横比（アスペクト比）が崩れてレイアウトが乱れるのを防ぐため、必要に応じてMarp独自のリサイズ記法やHTMLの `<img>` タグを活用してください。ローカルのファイルパス（保存場所）の記述エラーにも注意してください。
3. **品質チェック**: 
   - 1スライドあたりの文字数が多すぎないか？ 小見出しや箇条書き、キャプションなど可読性・判別性を意識できているか？
   - テキストの構造が正しいか？ 例えば、画像の反映漏れやマークダウン記法がそのまま出力（例： `**`, `[ページタイトル](ページリンク)` など）されていないか？
4. **【認知的チェックポイント】**
   - 生成した「1枚目の内容（およびスタイル設定）」をユーザーに確認してもらい、明示的な合意（Approve）を得ること。

### フェーズ4：一括生成と最終調整
テンプレート検証（お試し生成）で合意した「デザイン」と「文字量の感覚」を踏襲し、残りのスライドを一括で生成します。

1. **一括生成の実行（サブエージェントへの移譲）**: フェーズ1のアウトラインに従い、フェーズ2のスタイルを適用した全スライドの記述を一括で出力します。
   - **【実装の移譲】**: この**スライドのテキスト生成作業（Markdownの生成・保存）**はメインエージェントが直接行わず、**必ず `implementer-agent` サブエージェントに移譲**してください。
     - ※権限エラーなどにより `implementer-agent` が利用できない場合は、[`workflow.md`のサブエージェントの運用基準](../../rules/workflow.md#3-サブエージェントの運用基準)に則ったフォールバックを実施すること。
   - **【サブエージェントへ渡すプロンプト必須フォーマット】**:
     1. **コンテキスト・参照情報**: プレゼンの目的、トーン＆マナー、アウトライン構成案、非エンジニアへのテキスト説明方針。
      - 要約スライド作成時をはじめ、外部情報を参照している場合は、**ユーザーからの参照情報や外部ソースを「引用として必ず明記」するよう指示する**こと（※記載場所はスライド最終ページに箇条書きで良いが、複数ソースある場合は最終スライドとして引用情報を追加すること）。
     2. **技術構成**: Marp形式（Markdown + CSSのスタイル指定）。
     3. **実装内容と達成（完了）条件**: 全スライドのテキストを一括生成し、`tasks/` ディレクトリ配下にファイル作成すること。パスの整合性確認を必ず実施し、完了したらメインエージェントに報告すること。
     4. **参照用アセット**: フェーズ2で生成・指定した画像パス群、テンプレート検証（フェーズ3）で合意した1枚目のデザイン設定情報。
   - **【パスの整合性確認】**: サブエージェントは自律的に作成したMarkdown内の「画像ファイルパスの不手際（画像の反映漏れ）」や「マークダウン記法がそのまま出力されていないか」をチェックし、パスずれやリンク切れがないか確実に検証・修正を行ってください。
2. **HTML変換の実行と承認確認（メインエージェントの役割）**:
   - サブエージェントからMarkdownファイルの生成完了報告を受けたら、メインエージェントはユーザーに対し **「ファイルの生成が完了しました。続いて、Marp CLIなどを使用してHTMLへの変換処理（※）を実行してもよろしいでしょうか？ [y/n]」** と必ず承認を仰いでください。
      - ※HTMLへの変換時は **スライド画面内の分割表示（1スライド進むのに複数回のキー入力が必要となる状態）を完全排除し、直感的な 1 対 1 のスライド切り替え（`ArrowRight` / `ArrowLeft` / `Space`）を徹底する** こと。
   - ユーザーの承認（y）を得た後、メインエージェント自身がHTML変換コマンド（例： `npx @marp-team/marp-cli@latest presentation.md` など）を実行します。
      - **【変換時の画像パスリンク切れへの対応】**: HTML変換時に**高確率でスライドに挿入した画像パスの指定ミス（画像パスリンク切れ）が発生することが確認**されています。必ず画像パスリンク切れがないかをチェックし、修正・調整した完成HTMLをユーザーに提供してください。
      - **【変換失敗時の対応策】**: もしHTML変換コマンドが失敗した場合（システム環境のエラーやセキュリティ制限など）、エラー原因を特定し、セキュリティ制限の回避（`BypassSandbox: true`）や代替手段などの対応策を実行してください。
   - **【変換成功時の報告】**: 変換が成功した場合は、**必ずユーザーに対して「HTMLへの変換が成功しました。続いてブラウザでの確認フェーズへ移行します」と報告**してからプレビュー作業に進んでください。
3. **プレビューの案内（または実行）**: 変換したHTMLファイルをブラウザで開き、ユーザーにプレビュー確認してもらいます。プレビューの実行は**以下の優先順位**で試行・提案してください。
     - (1): **OS標準コマンドで開く（最優先）**: `Start-Process presentation.html`（Windows）や `open presentation.html`（Mac）を使用して既定のブラウザで開く。
     - (2): **Marp CLIのプレビュー機能（サーバーモード）**: CLIの機能でプレビューサーバーを立てられる場合はそれを使用する。
     - (3): **手動でのドラッグ＆ドロップ**: AIからのコマンド実行がうまくいかない場合、またはユーザーの環境制限がある場合、ユーザーに「生成されたHTMLファイルをブラウザのアドレスバーにドラッグ＆ドロップして手動で開いてください」と促す。
     - ※ブラウザでの確認時、ユーザーがスライドの修正を希望した場合はテキストやスクリーンショット添付などの指示による修正を受けられる旨を伝えて、ユーザーの希望に即した対応をしてください。
     - ※ブラウザ表示で不具合が発生した場合や、操作できない（または起動できない）場合： ユーザー許可を得てから `playwright-mcp` を使うか、ローカルサーバーの起動による回避を行うこと。
4. **【ユーザーからの修正指示への対応とアーティファクト運用の徹底】**:  
   - ユーザーから修正指示を受け取った際、AIは**作業着手前に必ず以下の文言をユーザーへ宣言**してください。
      - 「これより修正作業に入ります。`implementer-agent` サブエージェントに修正作業を移譲しますが『勝手な関連修正は行わず、指示箇所のみを修正』するよう明確に伝達します。修正後は、`qa-auditor` サブエージェントを用いて厳格に検証を行います」  
   - 宣言後、直ちにプロジェクト固有ルール（`workflow.md`）や実装計画書（`implementation_plan.md`）に規定されたチェックリスト（`task.md` など）を[アーティファクト](../../rules/workflow.md#2-プランモードと事前チェックリストの策定)として生成し、プランモードの運用を開始してください。
      1. **修正作業は必ず `implementer-agent` サブエージェントに移譲して**ください。
      2. **修正完了後の完了判定（検証）は必ず `qa-auditor`（専用検証サブエージェント）に移譲して**ください。※メインエージェント自身での自己検証（目視確認）は禁止とします。
      - ※権限エラーなどにより `implementer-agent`, `qa-auditor` が利用できない場合は、[`workflow.md`のサブエージェントの運用基準](../../rules/workflow.md#3-サブエージェントの運用基準)に則ったフォールバックを実施すること。
5. **最終出力の提案（PDFまたはPPTX（PowerPoint）形式でのプレゼン資料出力）**:
   - ブラウザでのプレビュー操作が完了した後、AIはユーザーに対して「最終的なプレゼン資料として、PDFファイルまたはPPTX（PowerPoint）ファイルにエクスポートして保存しますか？」と確認してください。
   - ユーザーが希望した場合、AIはMarp CLIを用いてPDFまたはPPTX形式への変換（例: `npx @marp-team/marp-cli@latest プレゼン.md --pdf -o presentation.pdf` または `npx @marp-team/marp-cli@latest プレゼン.md --pptx -o presentation.pptx` など）を実行し、出力されたファイルのパスを案内して作業完了を報告します。

</instructions>
