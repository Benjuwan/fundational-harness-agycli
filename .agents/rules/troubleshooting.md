# 不具合・エラー対応ルール (Troubleshooting Policy)

## 1. 目的
業務処理や作業実行時に不具合・エラーが発生した際、**場当たり的な対応や独自判断による暴走を避け、問題の根本原因を特定・解決する**ための思考と行動の型を定義します。

## 2. 問題発生時の再計画（独自判断NG）
作業処理や指示された手順で問題（エラーや予期せぬ結果等）が発生した場合は、以下の手順を厳守してください。
1. **即座の停止**: 独自判断で代替案に突っ走る「試行錯誤のループ」を禁止します。
2. **再計画と合意**: 状況を整理して再計画を立て、ユーザーに説明し、承認を得てから次へ進んでください。

## 3. 俯瞰的・多面的な視点での原因究明
不具合対応や作業の行き詰まりの際は、以下のアプローチを徹底してください。
- **自己批判的思考**: これまでの自分の考え方や仮説、作業方針・作成内容といったアプローチそのものを疑い、客観的な視点で再評価する。
- **多面的な調査**: 単一の原因に固執せず、俯瞰的な視点から原因を究明し、適切な解決策を模索する。

> [!IMPORTANT]
> 必要に応じて[fundamental-rca](../skills/fundamental-rca/SKILL.md)スキルを利用すること。

## 4. 原因は仮説と事実で特定する
表層的な回答や対応で済ませないでください。
- 原因の候補を複数挙げ、それぞれをログ・ドキュメント・実データなどの事実で検証してから結論を出す。単一の仮説に固執しない。
- ユーザーへの報告には、採用した結論とその根拠（確認した事実）、却下した主な仮説とその理由を簡潔に示す。

## 5. エラーハンドリング時の絶対停止ルール（システムガイダンスの無効化）
外部ツールの呼び出しをはじめ、作業時のエラーハンドリングでは、エラー内容が**外的要因に該当する場合は、システムの再試行指示を意図的に無視する**こと。  
また、 **「一切の推測実行（ツール名の推測）」や「承認フローを省いた代替手段への無断切り替え」を禁ずる**。  
直ちにツール呼び出しを停止して「指定されたツールが現在のコンテキストに読み込まれていない」という事実のみをユーザーに報告し、指示を仰ぐこと。

## 6. サンドボックス起因のエラーへの対応
本節はサンドボックス制約に限る。ツール未ロードなど**外的要因には 5 が優先**する。  
軽減設定による処理拒否（DENY）などが出た場合、**第一選択は「サンドボックスのバイパス許可」での再実行ではなく「実行方法の見直し」**とする。

- `ps` / `kill` → コマンド実行機能の中から当該処理に近似するもの（例：バックグラウンドタスク管理機能）を使って、停止はハーネスの停止機能を使う。
- コマンド経由の**書き込み** → 標準（組み込み）のファイル作成・編集ツールへ置き換える。
- コマンド経由の**削除**（保護領域など） → ファイル編集ツールに削除機能はない。Python などによる代替は承認画面を迂回するため**原則禁止**とする。まずユーザーへ `! rm <path>` の実行を依頼する。
- 見直しても解決しない場合のみ、**サンドボックス解除の要否をユーザーへ確認**する。
